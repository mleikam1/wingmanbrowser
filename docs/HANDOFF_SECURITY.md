## Trust boundary and startup

`HandoffController.initialize()` reads a dedicated secure-storage envelope before the root application constructs or loads owner browser/feature state. `HandoffGate` sits above the owner MaterialApp and Navigator. While the gate is loading, active or unavailable, it does not call the owner builder; its separate guest MaterialApp has no owner routes or offstage owner subtree. The root retains the owner's in-memory controllers outside the guest widget and can lazily initialize them after an authenticated return from a restored session.

Activation pins resource IDs and the signed catalog's content SHA-256 values. It validates each record through `ContentEligibilityService`, including owner-added restrictions in the preview. The session never admits a URL or caller-provided text. The signed policy is re-evaluated when the guest view rebuilds and on its expiry/revocation notifications. A missing approval, changed hash, unavailable policy or expired approval hides the shared body while keeping the owner gate closed.

The active marker, pinned IDs/hashes, random salt, verifier and retry state live in a single bounded, versioned secure-storage envelope. The active write and read-back must finish before guest text appears. Return requires successful code verification followed by a confirmed inactive write. The inactive record removes the session IDs, hashes and verifier from the logical record. Closing/backgrounding the app or disposing a controller never clears this marker. Restart reads it again before any owner content can appear.

Unreadable, locked, malformed, unknown-version or oversized secure state is not treated as an inactive session. It displays a fixed locked/unavailable view. There is no forgotten-code or storage-error bypass in Wingman. The owner is warned before activation. The app never clears normal browsing or feature data to simulate guest cleanup. Storage writes are serialized, and an operation that times out remains tracked until its native write finishes, preventing a late inactive write from racing a new session.

Return has an explicit commit point: the owner has entered the correct code, requested return and passed the interruption check. The subsequent inactive write completes that authorized action. Background/back before authorization cancels verification. Background/back after authorization does not pretend to cancel a write already sent to native storage. Until read-back confirms completion, owner widgets remain absent. A timed-out return is shown as unconfirmed, never as success; if its already-authorized inactive write later finishes, reopening can complete the return. This is disclosed rather than claiming an indefinite lock while the durable state may already be inactive.

## Owner-return authentication

This milestone uses an app-specific owner-return code, not OS biometric authentication. It reuses the existing isolate-based PBKDF2-HMAC-SHA256 implementation at 600,000 iterations, with a fresh 32-byte random salt and 32-byte verifier. The code itself is not persisted. Attempts are serialized and written before verification; retry delays begin after the fifth unsuccessful attempt and increase to a one-hour cap. Retry state survives restart, and a wall-clock rollback cannot remove an already spent attempt. Clock/device tampering by a privileged user is outside this ordinary app boundary.

Both setup and return use a custom numeric keypad. They create no `EditableText`, system keyboard/TextInput connection, clipboard action, autofill session, text selection or external context menu. Accessibility announces digit controls and the count entered, not the entered code. An app interruption invalidates in-flight verification before authorization. After the correct code has been verified, completing the durable return is an authorized owner action.

Native `handoffCapabilities` reads Android `KeyguardManager.isDeviceSecure()` or Apple `LAContext.canEvaluatePolicy(.deviceOwnerAuthentication)` without prompting or changing settings. Availability is queried rather than cached as evidence of a successful authentication. The dedicated Android emulator's read-only lock-settings inspection reported no credential and disabled lock screen; its runtime query returned false. The iOS simulator query returned true. This is the simulator API's reported prerequisite availability, not a verified OS authentication transaction or a physical-device result. No PIN, biometric enrollment or device setting was installed for the test. OS credential authentication is not advertised as implemented. [Android KeyguardManager](https://developer.android.com/reference/android/app/KeyguardManager#isDeviceSecure()), [Apple LAContext capability query](https://developer.apple.com/documentation/localauthentication/lacontext/canevaluatepolicy(_:error:)).

The secure-storage adapter uses Android's existing secure-storage plugin cryptography with **`resetOnError: false`** and a separate **`wingman.handoff.v1` storage namespace**. Version 11.1.0 otherwise defaults to destructive reset on some storage failures; that default is unsuitable for a durable owner gate. iOS uses nonsynchronizable, unlocked-this-device Keychain storage. Android app backup remains disabled. There is no plaintext SharedPreferences, normal SQLite, sync, or web-storage credential fallback. The active-session key is separate from the retired Guard PIN and from all normal feature state. Test fixtures use a separate fixed smoke key and never reset the production gate.

## Static guest capabilities

Guest articles are Flutter `Text` only. They contain no active hyperlinks, HTML rendering, scripts, image fetches, remote fonts, forms, selection controls, keyboard, file pickers, downloads, permissions, password-manager requests, exports, tabs/history UI, settings, suggestions, Spaces or task notes. Framework route requests resolve only to the guest screen. Native web/external capabilities remain unconditionally denied in every role/build. Incoming OS links cannot admit content or dismiss the root gate. A deny-only native `discardHandoffIncoming` operation clears the pending address, sets the owner incoming lifecycle to uninitialized, and drops subsequent guest addresses. The controller awaits this operation before activation, restoration and final owner-return authorization. Only the authenticated owner shell's ordinary `initialize` call resumes fixed address rejection, after clearing any old pending value. Root callbacks also require the owner shell to be mounted and the handoff gate to be open. Thus a queued guest link cannot reset the restored owner's tab/query after return. Disposal failures keep the gate unavailable; there is no URL-injection or external-opener channel.

Interactive isolation is deliberately unavailable. A separate widget would not establish website-storage isolation. Apple's nonpersistent data store and Android's profile APIs describe website storage lifetimes; neither establishes complete positive eligibility of changing page bodies, resources or authenticated state. Wingman has no current live-content adapter that proves all these properties, and none is reintroduced for this feature. [Apple nonpersistent website data store](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/nonpersistent()), [Android ProfileStore](https://developer.android.com/reference/androidx/webkit/ProfileStore).

Android's existing secure-window capture floor and iOS's existing neutral inactive-scene shield remain unchanged. They are not a device-wide kiosk. A guest can leave Wingman and use other apps or device controls allowed by the OS; Wingman does not control external password managers, OS settings or previously exported files in other applications. Rooted/jailbroken devices, debugger/memory inspection, malicious accessibility services, shoulder surfing and physical access beyond the app's normal UI are not defeated by this app-specific code. No forensic erasure or immediate physical disk deletion is promised.
