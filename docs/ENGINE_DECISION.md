Status: the ordinary consumer adapter remains Android System WebView. Production readiness is **not established** by the native unit suite. The actual-device acceptance matrix and unresolved gates are maintained in [DAILY_DRIVER_ACCEPTANCE.md](DAILY_DRIVER_ACCEPTANCE.md) and [RELEASE_BLOCKERS.md](RELEASE_BLOCKERS.md). ## Protection and compatibility boundaries

The retained adapter uses actual WebView networking, JavaScript, forms, browser cookies, DOM storage, browser navigation history and user-gesture media. Normal tab views are retained by the Flutter shell within its bounded live-view policy. Private profiles are genuine AndroidX profiles gated on the installed provider's multi-profile and deletion capabilities; unsupported providers must not claim private browsing. Site permission prompts remain native and bound to the initiating document/origin for media/location. HTTP-authentication is separately limited to the host metadata supplied by WebView. TLS certificate errors are canceled, HTTPS mixed content stays blocked, direct file/content access stays disabled, and no privileged JavaScript interface is installed into websites. `FLAG_SECURE` and disabled WebView inspection remain; new native authentication/permission dialogs are secure windows.

Third-party cookies are disabled. Some provider identity flows can require storage access, a supported external user agent, hardware credentials, or anti-bot checks. These require a specific observed failure and provider evidence; they cannot be relabeled as engine defects merely because a site refused a request. Reader extraction is not implemented by this Android adapter. Browser-engine support for readers, payment services, DRM or passkeys is not inferred from successful HTML rendering.

The [Android WebViewClient contract](https://developer.android.com/reference/android/webkit/WebViewClient#shouldInterceptRequest(android.webkit.WebView,android.webkit.WebResourceRequest)) exposes the initial subresource URL but not later redirect targets, and excludes some non-network schemes. Safe Browsing is a separate provider threat service and cannot fill Wingman's category-policy hook gap. Direct denied navigation and direct denied resources passing does not prove redirected resources are denied.

## Reproduced redirect-hook limitation

`prototypes/webview-hook-probe` is an isolated application and instrumentation test, not the consumer app. Its owned loopback server serves a neutral 1×1 PNG at a test-only denied path. On `emulator-5554` / WebView 151.0.7922.199, the direct PNG request was intercepted and denied before any server access. A permitted URL then returned HTTP302 to the same denied path: the server received that target once, the image loaded, and the native deny callback was not invoked for the redirect target. This establishes the specific API limitation without visiting prohibited material or modifying production category data.

Fresh execution at `2026-09-12 08:33:34` local time: **1 isolated instrumentation test, passed in 3.99 seconds**, where the pass means the expected defect was reproduced. Logs: `work/browser-readiness/webview-hook-probe-result.txt` and `webview-hook-probe-logcat.txt`. This count is not added to ordinary consumer acceptance or called a successful protection test.

The same owned probe was also installed on the new comparison device `emulator-5560` after its normal upgrade to WebView 151.0.7922.199. A fresh run again confirmed `directDenied=1`, `directTargetRequests=0`, `redirectedDeniedCallback=0`, `redirectedTargetRequests=1`, and `imageLoaded=true`. It completed one expected-defect test in 43.363 seconds including first provider initialization on the new device; this duration is not a page benchmark. ## Conditional GeckoView comparison

The stable candidate has been independently checked at Mozilla's live Maven repository: `org.mozilla.geckoview:geckoview:155.0.20260903215306`, repository `https://maven.mozilla.org/maven2/`. Retained metadata is `work/browser-readiness/geckoview-maven-metadata.xml`; the matching source revision in the POM is `5fdfd0092780e85643e2cddc0e1b590c8b9ef860`. The [official quick start](https://firefox-source-docs.mozilla.org/mobile/android/geckoview/consumer/geckoview-quick-start.html) specifies Mozilla's Maven source and Java 17. Nightly/central Javadocs are not used to assert the stable binary's APIs.

The isolated Android probe confirmed the material gap. The comparison is an isolated package/build under the same `wingman/protected-browser` method/event and `wingman/protected-web` platform-view contract. The normal adapter stays the default. It must not share the ordinary application's normal/private data, use an engine-selection preference, bypass policy, or import Firefox accounts, service credentials, telemetry settings or branding.

Gecko `NavigationDelegate` alone is not evidence for interception of every resource hop. A built-in trusted extension can use blocking `webRequest.onBeforeRequest` with permissions for both initiating and destination hosts. Mozilla documents that HTTP redirect processing starts the request lifecycle again. The listener must register synchronously at extension startup, avoid a tab-ID-only filter that excludes service-worker/background requests, and block network work until verified policy configuration is ready. Source: [Mozilla webRequest lifecycle and startup rules](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/webRequest). Non-observable targets and actual service-worker behavior still require fixtures.

The stable source exposes `ensureBuiltIn` and `setAllowedInPrivateBrowsing`. The [Mozilla extension integration guide](https://firefox-source-docs.mozilla.org/mobile/android/geckoview/consumer/web-extensions.html) documents bundled `resource://android/assets/` extensions. A prototype needs an authenticated background-only policy message channel and a ready acknowledgement before creating permitted browsing sessions; `nativeMessagingFromContent` must remain absent. Private extension eligibility must be enabled and verified before any private navigation. The sparse prototype overlay implements this path at `prototypes/geckoview/`; the 155 fresh host tests cover its policy/handshake logic, and the actual engine interception result is recorded below. Ordinary consumer UI acceptance remains a separate gate. The build script creates an external consumer-project copy so root Flutter analysis does not scan duplicate Dart sources.

The stable AAR requires compileSdk 37 and its AndroidX Core 1.19 dependency requires AGP 9.1 or later. Only the isolated copy uses compileSdk 37, AGP 9.1.1, Gradle 9.3.1 and Kotlin 2.4.10; targetSdk stays 36. The stable Gecko AAR manifest also requires **minSdk 26**, so only the prototype raises its minimum; production WebView retains minSdk 24. No manifest override bypasses that engine requirement. The [official AGP 9.1.1 compatibility table](https://developer.android.com/build/releases/agp-9-1-0-release-notes) supports API 37 and requires Gradle 9.3.1/JDK 17. The installed SDK license was already accepted before Gradle installed Platform 37.0. Production build dependencies are unaffected.

The prototype uses nonpersistent private sessions with separate context IDs, closes sessions before requesting scoped cleanup, and exposes `privateCleanupAcknowledgement: false`. Stable Gecko's scoped `clearDataForSessionContext` returns `void`; the acknowledged `clearData(ALL)` would also clear normal sessions and is not a suitable replacement. Private isolation tests therefore cannot be generalized to confirmed asynchronous deletion; that promotion gate remains unverified. The prototype also intentionally uses only the pinned baseline, without signed hot policy updates.

Promotion requires the same actual acceptance matrix, including keyboard/selection/focus/accessibility, normal/private storage, tab restoration, redirects and service workers, permission denial and origin binding, downloads, media, strict search, all mandatory category fixtures, TLS failures, renderer recovery and release native-library loading. Package size, app plus associated content-process memory, startup and tab switching must be measured on identified comparable builds. The specific redirected-resource interception improvement is now observed in the owned probe below. It does not establish the remaining promotion gates or justify switching the production default.

## Distribution and security maintenance

Current Android System WebView updates through the device's provider distribution; Wingman still owns monitoring supported versions, feature gates and regression tests. Bundled GeckoView changes the responsibility: Wingman must monitor Mozilla security releases, update the binary, rebuild, retest the policy and privacy gates, and ship the app update. Updating the operating system's WebView does not update bundled GeckoView.

GeckoView's POM identifies MPL 2.0. Distribution must retain required notices and provide recipients access to matching covered source; modifications to MPL-covered files remain under MPL, while independently authored app files need not become MPL merely through combination. Preserve third-party notices and avoid implying a Firefox trademark or service license. This assessment follows [Mozilla's MPL FAQ, questions 7–11](https://www.mozilla.org/en-US/MPL/2.0/FAQ/). A prototype release must include matching-source and license notices before distribution; this milestone does not authorize publication.
