## Cause and engine decision

Incorrect version gating, callback ownership, popup token handoff and a lost POST/opener relationship are Wingman integration/state defects. The milestone repairs these in their existing adapters where possible. iOS encoded-path resource handling was also repaired in WKWebView and tested with denied spellings and neutral positive controls. These issues did not justify replacing the engine.

The Android initial-resource-only redirect callback is different: the platform contract and a fresh real-network test reproduce a material engine-interface gap. That triggered the requested isolated GeckoView comparison behind the same Flutter/native interface. Its synchronously registered blocking extension uses the same pinned mandatory baseline and additional denies, with an authenticated background-only readiness handshake and private permission confirmation. It has no page message bridge or engine-selection preference.

**Gecko materially improves the specific redirected-resource enforcement gap.** On the matched API 37 / WebView 151 emulator, the ordinary WebView probe still loaded a denied redirect target once. The actual Gecko adapter with its bundled extension denied direct and redirected targets in normal/private image requests and normal service-worker fetches: each permitted control reached its server once and each denied target zero times. This is isolated native instrumentation, not consumer-site compatibility or private cleanup proof. Ordinary-site and performance results are separately scoped in the engine decision. The stable scoped cleanup call returns `void`; the prototype reports that acknowledged private deletion is unavailable, rather than clearing normal data to manufacture an acknowledgement. It has only the immutable policy bundle, not the consumer signed-update transaction. Promotion requires these gates and the same actual consumer matrix. Bundled Gecko security releases, matching-source/notices and shipping updates would become Wingman's responsibility. See [ENGINE_DECISION.md](ENGINE_DECISION.md).

Performance receipts identify both packages and every associated process. On the same owned API37/16KiB device, the held synthetic `/session` scenes measured **348,858 KiB summed PSS for WebView** (app plus one owned renderer) and **899,021 KiB for Gecko** (seven owned app/content/support processes). Gecko retained processes from the prior search/ESPN workload; these are not equivalent fresh-process histories. RSS is not summed. Three alternating cold-process activity starts measured WebView **4,312 / 3,164 / 1,520 ms** and Gecko **6,218 / 4,608 / 4,604 ms**. All reported success with new PIDs. Host load remained 118/183/267 with about 29.45 GB swap used; these observations do not establish an engine-speed or regression conclusion, nor first usable page timing. Receipts are `work/browser-readiness/performance/matched-{webview-session,gecko-session,cold-starts}/receipt.json`. The clean arm64 release footprint is **27.7 MB WebView / 220.2 MB Gecko** in the final release artifacts; the manifest identifies their hashes separately. Timed tab switching and representative physical-device benchmarks remain **Unverified**.

## Answers to the eight delivery questions

1. **Can I search normally?** The identified Android v12 build completed a fresh ordinary query and result navigation. Other-platform refinement remains unverified; no universal compatibility claim is made.
2. **Can I open and use ordinary result websites?** Android opened the ESPN roster and player statistics; the companion opened a real full NASA article. Android also completed controlled POST forms and file transfers. iOS opened a Walmart product and completed its live site search for pencils. More varied websites and several native tasks remain unverified.
3. **Can I read real fresh news?** Yes in the recorded web journey: actual approved NASA/NOAA/USGS content refreshed to the 13:44 UTC snapshot and remained available as a finite cached feed when its service stopped. The rebuilt Android consumer on the comparison device also fetched the 14:49 snapshot. The final iOS consumer also fetched the 14:49 snapshot and opened the new NASA article; full body scrolling remains unverified. No production feed endpoint is provisioned by this local test.
4. **Can I keep useful normal sessions without compromising private sessions?** The identified Android build preserved normal cookie/storage across reload and process death, isolated private state, and started a new private lifetime empty while retaining normal state. The final iOS consumer independently passed the same synthetic normal/private lifetime sequence and retained normal state and three normal tabs after termination/relaunch. Physical-device, interruption/provider variants and Gecko cleanup remain unverified. This is not a blanket guarantee for all login providers.
5. **Which permanent protections are actually enforced?** Validated local policy checks known category/threat domains, nine mandatory host/path rules, tracker domains and additional user denies; known searches use the strict provider and autocomplete preference. Invalid mandatory data or uncertain policy generations close browsing. iOS has real WK resource-rule test evidence. Android's later resource redirect hops remain a known gap. Unknown permitted sites are not certified safe; these are URL rules, not a full text/image classifier.
6. **Which limitations remain?** The documented redirect/category gaps, narrow promotion datasets, incomplete native matrix, exact-origin HTTP-auth uncertainty, private popup edge cases, physical-device coverage, performance comparison, production signing/entitlements, and operating owners/feed keys/endpoints remain. SafeSearch is adult filtering, not the full six-category policy. The companion delegates outbound browsing to its host.
7. **Did GeckoView improve anything materially?** Yes for one material gap: actual normal/private image requests and normal service-worker redirects remained blocked where WebView's resource hook leaked the redirected target. This does not pass the broader compatibility, deletion acknowledgement, signed-update and performance promotion gates. The working consumer adapter remains intact.
8. **What build should I open to test it?** Use the ordinary **0.12.0+12 consumer** build from `lib/main.dart`, identified in the artifact table. Start with the final arm64 **profile** APK to review the repaired consumer and configured local feed. The release APK is a separate build-validation artifact with no provisioned production feed.
