# Recovery requirements audit

Audit date: September 11, 2026. Scope: the original consumer reset brief, current source, and updated recovery records. This is an independent source/evidence audit, not a blanket claim of completed browser recovery. The confirmed ordinary-app journeys are recorded in [SEARCH_ACCEPTANCE.md](SEARCH_ACCEPTANCE.md); remaining checks are distinguished below.

The architecture now permits ordinary consumer destinations under a mandatory local baseline, keeps school/catalog authority separate, uses native browser networking, and preserves normal renderer ownership across overlays. Those changes address the original exact-document failure. Full recovery remains gated by the following work.

## Release checklist

- [x] **Repair search-to-website navigation and demonstrate the required search/domain scale.** Android recorded 12 queries and 10 ordinary result domains; iOS recorded 11 queries and 10 domains. No counted destination was added to the pilot's exact-document allowlist for acceptance. Both included ESPN and Walmart. Android also exercised provider refinement and More Results. The web companion actually submitted a query by top-level strict-provider navigation.
- [x] **Run the full host checks and retain separate evidence.** Full Flutter suite: 736 passed, 2 optional skips; full project analysis: no issues. These results are logged in `work/consumer-recovery/full-tests-final.log` and `analyze-final.log`; they do not substitute for device journeys.
- [x] **Build the final web artifact and retest the Android find repair.** Web release build passed in 460.8 seconds (`work/consumer-recovery/web-build-final.log`). The final Android release install retained normal cookie/storage across debug-to-release replacement; Find highlights, Next and Done worked without the earlier crash. Eight Android JVM verifier/search tests passed.
- [x] **Separate auxiliary native events from navigation validation.** A URL-free `findResult` previously entered page-URL validation and could suspend/hide the current page. The event handler now validates URLs only for `pageState`; the added regression checks unchanged page status and successful subsequent navigation. This repairs a separate defect from the earlier Find-dialog dismissal assertion.
- [ ] **Configure and demonstrate the secure consumer update pipeline.** Since the initial audit, a consumer-specific Ed25519 verifier, HTTPS transport, transactional active/previous/pending cache, replay protection, native preparation/activation/revert protocol and interrupted-update recovery tests were implemented. Startup integration restores before creating renderers. No production signing key or feed is configured; keys are deliberately empty. Complete a real signed-feed update/restart/failed-compilation/recovery demonstration on both platforms before closing this gate. The existing optional Guard updater remains separate. See [CONSUMER_PROTECTION_UPDATES.md](CONSUMER_PROTECTION_UPDATES.md).
- [ ] **Replace the three small mandatory-category supplements with maintained coverage.** Licensed maintained NSFW, Gambling Mini and Threat Intelligence Mini sources supply substantial coverage. Alcohol, recreational-drug commerce and tobacco/vaping currently have only 16, 11 and 17 domains respectively, plus a few paths. They cannot support broad category-enforcement claims. Any replacement must preserve educational/medical/recovery distinctions and include a correction process; a larger indiscriminate list is not sufficient. Known matched entries remain non-overridable.
- [ ] **Close Android resource redirect enforcement gaps.** `ProtectedWebBridge.kt` returns allowed resources to Chromium after the exposed initial request check. Android does not repeat `shouldInterceptRequest` for subsequent resource redirects. An allowed image/script request can consequently reach a blocked resource destination without a local recheck. Main-document and downloader checks do not cover this gap. Generated content and WebSocket coverage also remain limited. The brief's “no protection bypass through redirects” criterion cannot be marked complete. See [Android implementation and API limitations](ANDROID_BROWSER_RECOVERY.md).
- [ ] **Verify iOS resource rules independently from navigation policy.** WebKit compiles literal URL/path rules while native document checks also decode and normalize paths. Host policy tests and successful rule compilation do not prove equivalent behavior for encoded/dynamic resource URLs. Exercise the actual WKWebView with synthetic resource/redirect fixtures and measure full-list startup, memory and recovery on device. See [iOS verification](IOS_CONSUMER_ACCEPTANCE.md).
- [ ] **Finish the remaining ordinary-app feature matrix.** Both platforms demonstrated fixture JavaScript, GET forms, POST login/storage, normal persistence across replacement, private isolation/non-restoration, native back/forward, permitted/blocked redirects/windows, invalid-TLS rejection and an OS-picker upload/download round trip. Both also exercised provider-field refinement and More Results. iOS generated media played with native fullscreen entry/exit and an origin-named camera prompt denied access. iOS visible find highlighting, touch scrolling and physical-device checks remain unverified. See [Android evidence](ANDROID_BROWSER_RECOVERY.md) and [iOS UI acceptance](IOS_UI_ACCEPTANCE.md); simulator keyboard paging does not prove touch scrolling.
- [ ] **Validate remaining native feature boundaries.** Ordinary-app OS picker/export and media execution are recorded; origin permission denial is verified, while grants, microphone/location and physical-device behavior require further evidence. Blob downloads and complex POST new-window flows remain unsupported; HTTP-auth/client-certificate/WebAuthn/provider-specific sign-in compatibility is incomplete or unverified. Do not advertise these as fully working solely because capability flags or methods exist. Document any accepted milestone scope explicitly.
- [ ] **Obtain and validate iOS default-browser entitlement.** Incoming-link handling is implemented, but Apple's managed `com.apple.developer.web-browser` entitlement is absent and capability correctly reports unavailable. A build flag or URL registration alone is not the grant. Android’s system browser-role chooser selected Wingman as default and the role was read back. External-app cold/warm link taps remain unverified; resolver registration alone is not that UI demonstration.
- [ ] **Resolve remaining platform validation and preserve configured-service reporting.** Completed host checks, final web build and Android release evidence are recorded. iOS build-for-testing passed, but XCTest could not launch its host after approximately eight minutes (`CoreSimulator host_support_mig_launch_app`); those tests were not executed. This tooling failure does not erase ordinary-app UI evidence and must not become a test pass. The protection-details UI presents installed data date and stale-data warning; preserve the distinction from a configured live update service. No production feed or comprehensive category coverage should be implied. Neutral ESPN's observed betting promotion is recorded alongside successful navigation.

## Boundaries already represented honestly

The web companion performs top-level strict-provider navigation and relinquishes control to the host browser; it is not a desktop browser binary. Search-provider adult filtering does not classify gambling, alcohol, drugs, tobacco or every result preview. User-added restrictions are subtractive. Normal platform stores persist; private sessions use separate stores/profiles and are not restored. Four retained engines bound memory; an evicted tab can reopen its last URL without a promise to restore its full history, form state or scroll. These are explicit product limits, not failures to reproduce.

The final full host suite recorded 736 passes and two optional skips; project analysis was clean. Supporting focused evidence includes 35 signed-update/baseline passes, including callback timeouts and SQLite recovery. These results substantiate local contracts only. The final query and platform ledgers remain the authority for actual browser behavior.
