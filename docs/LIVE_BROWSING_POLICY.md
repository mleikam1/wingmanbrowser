# Wingman live browsing policy

> This document defines the six reviewed website scopes. Version 0.9 also permits the separately controlled provider results surface described in [Strict search](STRICT_SEARCH.md). That provider surface has an adult SafeSearch filter, not full Wingman content classification; it grants no destination permission.

Review date: **September 11, 2026**. This milestone adds a constrained live-rendering capability beside the existing signed offline library. It does not certify general website compatibility or claim perfect content classification. The mandatory categories remain application rules; a favorite, role, private session, edited shortcut or familiar brand cannot disable them.

## Authority and scope

`assets/policy/live_sites.json` is a separate build-bundled network-scope manifest. Its exact bytes are pinned by SHA-256 in Dart and independently in each native renderer. The manifest is not accepted from a website, local preference or MethodChannel payload. Changing an enabled flag, adding a host or replacing an image URL invalidates the complete asset until a reviewed application build updates all pins. This is an application-release mechanism, not a remotely signed update service or a production signing-key solution.

The manifest has schema version 1, sequence 1 and mandatory policy version 1. Its review window is September 11 through **October 11, 2026, exclusive**. Site review windows cannot exceed the manifest window. The Dart evaluator uses the existing policy runtime's checkpointed clock when integrated into navigation. Expiry, unavailable native capability, a damaged asset or unavailable mandatory policy closes live eligibility.

Each site record contains an explicit enabled state, stable ID, entry URL, title, description, collection, permitted contexts, review dates, exact document URLs, exact passive-resource URLs and limitations. Each resource declares its intended type and MIME/size limits. Documents, images, style sheets and fonts are distinct; permission to show an image beneath a reviewed document does not make that image an approved top-level page. There are no host wildcards. Fragments can navigate within an eligible document; changing its query does not inherit approval.

`LiveBrowsingPolicy.assessNavigation` returns the existing `PolicyDecision` type. It recognizes disabled candidates for explanation but cannot allow them. Additional restrictions subtract by live site ID or collection. `assessResource` is the corresponding policy oracle: the parent document must still be eligible, the method must be GET, the resource type and complete URL must match, and a matching third-party privacy rule can only remove permission. A nested document is not a passive resource.

Native code must independently enforce the same build-pinned scope; a Dart approval cannot manufacture native capability. The public live path has no script-evaluation API or unreviewed raw-loader fallback. Web companion editing and offline tools do not become an unrestricted website proxy.

## Enforcement and classification are different

The prototype applies locked request rules before supported network consumption and uses native maintained renderers with JavaScript disabled. Android's mediated HTTPS fetch path rejects redirects, inspects MIME and bounds response bytes. Ordinary `shouldInterceptRequest` alone sees only the initial resource URL during redirects and does not cover every special URL; the independent fetch/default-deny design must be verified rather than relying on one callback. [Android WebViewClient](https://developer.android.com/reference/android/webkit/WebViewClient)

iOS uses compiled WebKit request rules and scriptless navigation controls. WebKit resource-type rules describe the intended use of a request, not a guarantee about the response's MIME or bytes. WKWebView does not provide the same pre-consumption HTTPS response-body inspection or per-resource byte cap as Android's mediated fetcher. The manifest's byte/MIME declarations must therefore not be advertised as equivalent enforced limits on iOS. [WebKit content blockers](https://webkit.org/blog/3476/content-blockers-first-look/)

An approved URL can change tomorrow; a permitted image filename does not prove its pixels safe. There is **no deployed visual classifier**, no automatic six-category page classifier, and no server that reviews every response. There is no promise of zero offensive material across the entire Internet. The practical boundary is a small reviewed, scriptless scope with known exclusions, revocation/expiry and native request controls. Expanding the live catalog requires content review and device verification; bypassing the restrictions to make an incompatible store or sports site render is not an acceptable completion step.

## Maintained privacy data and attribution

The separate privacy field expands the obsolete seven-domain starter to **2,501 exact supported third-party domain rules** selected from EasyPrivacy. It is a subtractive layer beneath the positive passive-resource scope. No browsing URL is sent to EasyList, Wingman, Firebase or a classification API to decide whether a request matches.

Same-host requests are not classified as third party. No cosmetic filters, scriptlets, path syntax, wildcard patterns, resource-type modifiers or exception syntax are interpreted.

This is a supported subset from one upstream file, **not all of EasyPrivacy**. It does not include the full list's exception engine or a public-suffix domain parser. The exact positive scopes remain the main boundary. Privacy data does not classify gambling, drugs, alcohol, nicotine or adult imagery, and does not replace threat intelligence. No complete live six-category database or production category-provider agreement is claimed. A fresh reviewed build is needed before this snapshot expires; automatic update infrastructure is not silently enabled.

The app registers the source attribution, modifications and full license with Flutter's existing **Open-source licenses** screen. `tool/policy/build_live_privacy.py` reproducibly regenerates a separate review artifact from the pinned upstream source, checks its digest and 2,501-rule count, and never activates a manifest or changes an application pin. It can use an already downloaded file to run without network:

```sh
python3 tool/policy/build_live_privacy.py --source-file /path/to/reviewed-source.txt --output /path/to/new-review-artifact.json
```

Without `--source-file`, the maintainer command requests only the pinned public upstream file. It does not run at application startup. It refuses to overwrite the destination. Verification reproduced the bundled privacy JSON exactly. `python3 tool/policy/check_live_manifest.py` independently checks all three application pins against the current asset and prints the scope counts; it is read-only and does not enable sites or extend review dates.

## Privacy, operation costs and release checks

The policy asset is 289,663 bytes and travels with the app; rule decisions are local. Its build pin is `7937170f4c5605faff4e7fbfcc0ea4f27623b05a75c84e6adc8aba2243f965c1`. No Firebase document read, cloud function, image-classification call, paid API subscription or browse-through server is required per page. Website requests still expose the user's IP address and ordinary request metadata to the visited origin and permitted asset services. The renderer's cookie, cache, storage, referrer and private-session behavior must be stated from the actual platform tests; the local rule engine does not itself make the network anonymous.

Before expanding a scope, review its rendered page, passive dependencies, redirects, shared navigation, recommendations, MIME changes and geographic differences. Keep challenge/login/paywall handling unsupported unless an independently reviewed interaction path exists. Test policy expiry, added restrictions, session changes, backgrounding and handoff while requests are pending. No automatic new-host approval, post-display blur, CSS removal of a few links or unchecked fallback can substitute for that evidence.

The 17-test Dart suite in `test/policy/live_browsing_policy_test.dart` passed in the complete **528-pass, 2-optional-skip** host run. It covers pinned loading, exact document/fragment/query boundaries, malformed and local targets, disabled candidates, expiry, additional restrictions, contexts, parent-bound passive resources, method/type/redirect denials, immediate revocation, tracker suffix boundaries, asset tampering/size failure, immutable records, all three source scopes and cross-source resource isolation. Detailed host/native results are reported in milestone QA. A Dart test cannot prove native network enforcement or real image rendering.

The test-only `ios/RunnerTests/RunnerTests.swift` fixture **passed in real WKWebView on the dedicated iPhone 17 Pro / iOS 26.3 simulator**, with `xcodebuild` exit 0 and a 2.051-second test body. It compiles the production `protectedContentRuleJSON` builder into a real WKContentRuleList. The owned loopback server observed exactly one document, allowed style sheet, allowed image and initial redirect request. The allowed image decoded at four pixels wide; the exact `%7C`/`%2C` CSS query matched and applied the expected `sans-serif` font, with one external style sheet. Unreviewed redirect target, direct image, style sheet, CSS background, iframe and script requests all remained at zero. This does not grant localhost permission to the application: it has no production override, app-channel raw loader or ATS configuration change.

Evidence is retained in `work/live-native-webkit-xctest-final.log`. The earlier attempt failed before the test body because the simulator was unavailable; a subsequent body execution demonstrated the expected network behavior but failed its image-size assertion because UIKit generated the four-point fixture at the simulator's 3× scale. The fixture now explicitly uses scale 1. No production request rule was relaxed. The final invocation used `FLUTTER_TARGET=lib/main.dart`, only this XCTest and `-parallel-testing-enabled NO` to avoid launching a cloned simulator. This verifies the tested WebKit request/redirect behavior and exact-query style matching; it does not establish universal content classification or every live site's layout.
