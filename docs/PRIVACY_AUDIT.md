# Privacy and security implementation review

Phase 2 adds local Guard controls and secure PIN storage. Its current data-flow, endpoint inventory, audit findings and verification scope are documented in [Privacy architecture](PRIVACY_ARCHITECTURE.md). The baseline review below remains the Phase 1 record.

Reviewed September 10, 2026 against the mission **“We've got your back, not your data.”** This is a source review and focused automated verification of the local working tree. It is not a penetration test, a final signed-binary attestation, or a store-readiness claim. See [privacy architecture](PRIVACY.md), [native browser details](NATIVE_BROWSER.md), and [release checklist](RELEASE_CHECKLIST.md) for the operational limits.

## Scope and evidence

The review covered application Dart under `lib/`, app-owned Android Kotlin/manifest and iOS Swift/Info.plist, persistence tests, ad tests, and the production source differences in the vendored WKWebView plugin. Upstream sample applications and generated build outputs were excluded. Third-party SDK internals and remote website behavior were not comprehensively audited. The exact linked SDKs remain relevant even when application code never uploads browsing data.

| Boundary | Implementation evidence | Assessment |

| No browsing telemetry | `lib/privacy/product_analytics.dart`, `diagnostic_sanitizer.dart`; application source scans | No analytics backend or separate analytics/crash/attribution SDK is configured. Analytics accepts only enum events and defaults to a no-op. Diagnostics drop hosts, paths, queries, fragments, credentials and raw error descriptions. No direct application logging calls were found in the reviewed production source. This does not cover every OS/SDK diagnostic. |

## Findings addressed during review

The review led to narrow fixes rather than added services: stale authentication and permission-result checks, correct HTTP-challenge labeling, stale Android file-picker and external-launch guards, geolocation context checks before the OS prompt, safe false/empty JavaScript dialog results after a context change, a cold-start cache-clear path, truthful storage-error feedback, tighter content-resource settings, and cancellation of delayed Home consent work. Android's publisher first-party-ID setting was moved after the explicitly gated SDK initialization and before the first request because calling it at application startup caused a native crash. The SDK is not initialized automatically to work around that requirement.

The vendored `webview_flutter_wkwebview` 3.26.1 production source was compared against the installed pub.dev package. Exactly three source files differ: the Dart creation-configuration identifier getter, the native configuration lookup, and a lint-only comment preserving upstream Apple constant names. The two small API additions expose configuration to the Flutter app, not to website JavaScript. Generated Pigeon protocols and upstream navigation/TLS behavior were not modified. [Patch description](../third_party/webview_flutter_wkwebview/WINGMAN_PATCH.md)

## Verification performed

Source scans of application Dart, Kotlin and Swift found no direct `print`/`debugPrint`/platform-log calls, website-native bridge registrations, or `registerWebView` calls. There is one application `AdRequest` call and one Home ad construction site, separate from the widget constructor declaration. These scans support the manual call-path review; regex absence alone is not proof of privacy.

The ad/consent/privacy suite passed **19 tests** after the final required-form load/presentation cancellation change. It includes Home disappearance during UMP update, options-requirement lookup, and form loading; failed updates; changed consent; forbidden routes; private exclusion; release denial; and diagnostics. Targeted analysis of the changed monetization code and tests reported no issues; analysis of all `lib`, `test` and `integration_test` sources also passed. Immediately before that last adapter change, the combined ad/privacy, SQL repository, state and URL-parser run passed **86 tests**. The data and parser sources were not changed by the consent fix.

The real iOS simulator ad smoke was rerun **after** the final separate form-load/presentation cancellation change and passed. It reported `actualBannerRendered: true` and `outcome: bannerLoaded` using Google's approved test inventory and the real UMP flow. It never clicked the creative. It also removed Home during a pending consent operation and reported `pendingAtUnmount: true`, `noAdAfterUnmount: true`, and only `consentStarted` then `disposed` for that cancelled slot. The replacement surface received no ad or later lifecycle callback. The Xcode build took 49 seconds; the integration test took 21 seconds. The actual consent region was not overridden, so focused tests provide the separate evidence for cancellation while a required form itself loads. This native result covers the updated ad adapter on that simulator, without asserting physical-device or production account readiness.

## Remaining disclosures and release checks

Google's ad/consent SDK can process technical device, network, interaction and diagnostic information. Non-personalized requests, disabled publisher first-party IDs, removal of Android AD_ID permission, disabled mediation initialization and iOS SDK crash reporting reduce selected behavior; they do not prove zero SDK collection. The mobile SDK remains linked even with the demo off and has no general shutdown API after initialization. UMP has no programmatic dismissal used here for a form that is already on screen. Production ads remain disabled pending real account configuration, regional consent tests, SDK traffic inspection and consistent store disclosures. See the primary-source links in [privacy architecture](PRIVACY.md) and [monetization](MONETIZATION.md).

Private mode does not hide website or search requests from their recipients, encrypt the application's database, erase user exports, or establish perfect disk erasure. Android transient profile writes and cleanup after an unclean exit are specifically disclosed. Backup exclusion of the iOS structured-data folder does not establish backup treatment of every normal WebKit file or download. The web companion cannot control or clear another browser's sessions.

Physical-device permission/upload/download behavior, broad website compatibility, all UMP regions/age scenarios, final merged manifests/privacy manifests, production signing, Apple browser entitlement/provisioning, published privacy policy/operator details, and store declarations require the final release review. Final compile, full integration reruns and commit identity belong to the project's validation report; this review does not claim they are complete.
