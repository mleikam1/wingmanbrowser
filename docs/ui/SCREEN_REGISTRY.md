# Screen and flow registry

Current implementation inventory: September 11, 2026, `ui-handoff/implementation`, application 0.6.0+6. Starting application commit was `d5ca5ba7087e91f7f50b3b073960f7187a767e69` (0.5.0+5). This maps all **51 written handoff IDs** and additional reachable overlays. The starting audit is preserved separately in [UI_AUDIT](UI_AUDIT.md); this table describes the implemented app.

**Status vocabulary:** `Implemented` means the supported production route is connected to actual local state/actions. `Capability-limited` means a specific live/platform operation is unavailable and has an honest explanation; it does not mean that its surrounding local UI was omitted. Gallery-only transport errors are explicitly marked. Actual final test/build/device results are recorded in [QA_REPORT](QA_REPORT.md); a route row alone is not release certification.

**Platforms:** `All` means Android, iOS and the Flutter web companion for local content, subject to valid policy/storage. `Native` means supported Android/iOS capability only. Offline is the normal operating condition for the reviewed catalog and local tools, not a simulated web connection. There is no live WebView, network search, site account, permission request, media renderer or website download flow.

**State notation:** rows name applicable states and missing state treatments. Every local read/write also needs storage-failure treatment where persistence is involved. Website loading, site permission denial, TLS retry, network progress and third-party account states are **not applicable** to a purely local screen; they must not be rendered as working capabilities. Private and edition scope are evaluated by the real state/policy services. Policy expiry/revocation can remove previously visible resources.
