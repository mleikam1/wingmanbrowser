# Launchpad UI implementation and evidence

This extends the existing Home module and tracked feature routes. It does not create a second browser, add website capability, or change content approval. Core model/storage details are in [Launchpad specification](LAUNCHPAD_SPEC.md); native and website evidence belongs in [Site compatibility](LAUNCHPAD_SITE_COMPATIBILITY.md) and [Launchpad QA](LAUNCHPAD_QA.md).

## Connected interaction inventory

`lib/presentation/launchpad/launchpad.dart` exports the production widgets. `LaunchpadSection` is embedded below the existing Home search. It shows up to eight saved shortcuts/folders, an explicit expand control, Add and Edit. Ordinary 390px phone content uses four columns; narrow layouts and large text use fewer. Tile height follows wrapped content. Local icons/initials replace remote favicons. Folder previews contain small local icon mosaics, with revoked resource icons and titles redacted.

`LaunchpadAddScreen` provides suggested entries with multi-select/count, typed address, eligible bookmarks, and local tools. First-use selection can be dismissed durably. Suggestions show current eligibility, inspectable scope/provenance and canonical addresses; reference addresses are plain text, not outbound links. Existing pins are labeled rather than duplicated. Website candidates require explicit inactive-record consent. The save action never claims submission to a review service.

`LaunchpadEditorScreen` previews the normalized destination, editable name, local icon/one-to-two-character ASCII initials, and folder. Names are rendered as text. An address edit receives a fresh eligibility decision; catalog provenance cannot transfer to another destination. A revoked resource form hides retained metadata. No title, artwork or preview lookup is sent as text is entered.

`LaunchpadManageScreen` and `LaunchpadFolderScreen` expose Open, resource-only New tab, Edit, Move to folder, Move up/down, and Remove. Long press and secondary pointer actions open the same editing controls; visible Edit supports keyboard access. Each full-list row also has a keyboard-visible Organize action opening its existing single-item panel. That panel retains the actual sibling order while keeping its controls in place for consecutive keyboard moves. Reordering saves immediately through atomic controller operations. Dynamic item/source rows and collection groups have stable identity keys, so state follows the record rather than its former list position. The initiating reorder control remains focusable during a pending write, while a busy guard rejects duplicate activation; no completion callback moves focus after the user tabs elsewhere. Selecting the current folder is a no-op. Removing a nonempty folder explicitly offers either moving its shortcuts to Home or removing the group. Undo uses a controller-owned token and restores no permission. Folder input controllers outlive the complete reverse dialog transition.

`LaunchpadCustomizeScreen` controls shortcut visibility/density, collections and existing Home-section/Spaces callbacks. Restoring suggestions is confirmed and only reopens the picker; it does not overwrite edits or repin removed defaults. `LaunchpadCollectionsScreen` renders saved collection order and supports visibility, order and removal. `LaunchpadSourcesScreen` adds/removes/reorders finite selected sources using queued field updates. Revoked or retired sources have a redacted removal action. Bookmarks, shortcuts, collection choices and Spaces have distinct ownership. A selected eligible resource can be explicitly added to a Space via the shell's picker.

## Session and safety contract

The shell supplies `LaunchpadActions`: a captured-origin predicate, tracked route push, open callback, eligible bookmark getter, current policy/state changes, catalog, and optional Space/Home-section callbacks. Widgets do not call WebViews, external launchers, networks or policy override APIs. Every save/open consumes the core eligibility adapter again. Only resource targets offer New tab; tools use feature routes and website candidates remain inactive.

Normal and private controllers are separate. Private UI hides normal bookmark drafts and retains only its session's own shortcuts. All editable fields disable autocorrection, suggestions and personalized IME learning, and retain only the existing local cut/copy/paste/select-all menu. These settings do not claim control over every third-party keyboard.

Queued mutations capture a route/lifecycle generation. Covering a route or backgrounding invalidates an outstanding action permanently, even if the user returns before its queue turn. An owned confirmation can cover its parent once; another route covering that dialog or a lifecycle interruption cancels it. A previously dispatched durable write may complete, but a stale result cannot redirect or present success in another scope. Storage errors stay inline and retain prior records.

## Verification

The focused functional suite is `test/launchpad/launchpad_ui_test.dart`: multi-select/dismissal, normalized inactive addresses and credentials rejection, rename/initials/address change, canceled/failed writes, both folder deletion choices, move-out/undo, same-folder no-op, persistent non-drag order, collection source ownership/order/visibility, explicit Space callback, revoked source removal, restore confirmation, long press and actual Tab/Enter access, resource revocation, private isolation, and delayed queue cancellation after route/background return.

`test/launchpad/launchpad_layout_test.dart` mounts each intended screen independently and asserts that exact widget instance is present. Six routes × eight widths (320/360/390/430/600/768/1024/1440) × 100%/200% text × light/dark cover 192 render states. The 390px grid asserts four columns, eight initially visible tiles and 48px minimum targets. Representative phone captures use the real widgets, real catalog icon presets and synthetic local records; they do not show an external website or a real user's data. A first capture harness incorrectly retained the initial Navigator route; those misleading images were replaced after fixing unmounting and adding an exact-scene assertion.

The corrected matrix run passed **19 tests in 13s**: the then-current 17 functional cases and two matrix cases covering those 192 actual render states (`work/launchpad-ui-layout-final.log`, parent workspace). The command from the repository root was:

```sh
flutter test --no-pub --dart-define=WINGMAN_CAPTURE_LAUNCHPAD=true test/launchpad/launchpad_ui_test.dart test/launchpad/launchpad_layout_test.dart
```

Actual release Web keyboard QA subsequently found that unkeyed rows could transfer focus to another record after Move up. Two Tab/Enter regressions now cover a root folder and a shortcut inside a folder. The root case pauses the document write across rendered frames, checks focus while pending, verifies that repeated Enter does not enqueue another write, then checks the same FocusNode/action before a second successful move. Both cases passed in 1s (`work/launchpad-keyboard-delayed.log`), and the complete **19-case functional suite passed in 7s** (`work/launchpad-ui-focus-final.log`) after the identity and busy-focus fixes.

Actual Web retesting distinguished Flutter widget focus from browser DOM focus: a moved row can retain its Flutter FocusNode while the browser focus falls back to the page. Stable keys prevent another record receiving the action, but do not repair that engine behavior. Flutter documents that Web semantics focus follows DOM focus, and its direct [FocusSemanticEvent](https://api.flutter.dev/flutter/semantics/FocusSemanticEvent-class.html) supports Android/iOS only. Wingman does not force browser blur/refocus or mutate the engine/DOM. The visible Organize workflow instead opens a single-item panel, so its reorder controls do not move with the sibling list. The focused test uses Tab/Enter to open that panel, then repeats Enter twice, checks actual sibling order, confirms other rows are absent and retains the same panel/action FocusNode. It passed in 1s (`work/launchpad-organize-keyboard.log`), followed by the complete **20-case functional UI suite passing in 7s** (`work/launchpad-ui-organize-final.log`). The actual release Web workflow also passed: Tab/Enter opened the folder's single-item panel; the first Move up changed sibling index 2 to 1 while retaining the same DOM element (`flt-semantic-node-119`) and accessibility focus, and the second Enter moved it to index 0, where Move up became disabled. See the [actual Web keyboard capture](launchpad-screenshots/web-organize-keyboard.png) and [Launchpad QA](LAUNCHPAD_QA.md).

Representative 390×812 captures: [Grid light](screenshots/launchpad-grid-light.png) / [dark](screenshots/launchpad-grid-dark.png), [editor light](screenshots/launchpad-editor-light.png) / [dark](screenshots/launchpad-editor-dark.png), [management light](screenshots/launchpad-manage-light.png) / [dark](screenshots/launchpad-manage-dark.png), [suggested picker light](screenshots/launchpad-suggested-light.png) / [dark](screenshots/launchpad-suggested-dark.png), [customization light](screenshots/launchpad-customize-light.png) / [dark](screenshots/launchpad-customize-dark.png), and [collections light](screenshots/launchpad-collections-light.png) / [dark](screenshots/launchpad-collections-dark.png).

Inspection confirmed distinct actual routes, real local icon choices, clear inactive-state warnings, multiline controls and saved collection ordering. Long user/tool labels wrap rather than disappear. One address helper initially ellipsized; it now allows eight helper lines. After the final capture-enabled whole-suite run, all twelve images were opened and inspected, including the corrected light/dark editor privacy explanation, which now wraps completely. Screens mounted as a capture root intentionally have no app-back button; production feature navigation retains the shell's tracked route stack. Full-host, actual release Web, native integration, build and physical-device evidence must not be inferred from these widget tests. The final combined host run passed **486 tests**, with two optional benchmark skips, in 39s (42.63s wall time; `work/launchpad-final5-test.log`); full analysis was clean in 2.4s (3.70s wall time; `work/launchpad-final5-analyze.log`). The release Web build passed in 30.9s (31.54s wall time; `work/launchpad-final5-web.log`). The run included the corrected matrix and regenerated the linked captures; the refreshed grid-light and editor-dark images were opened again and confirmed to show the intended distinct scenes with the full address-helper explanation. The final management-light capture was also inspected and includes the Organize guidance. Actual Web/native interaction results and build limitations are maintained in [Launchpad QA](LAUNCHPAD_QA.md).

## Interaction research

The implementation borrows familiar explicit add/edit/folder patterns from Opera's official [desktop Start page](https://help.opera.com/en/latest/start-page/), [iOS Start page](https://help.opera.com/en/mobileios/start-page/) and [Android customization article](https://blogs.opera.com/mobile/2026/08/five-ways-to-get-more-out-of-opera-for-android/). Wingman uses its own identity and local icon assets. No Opera artwork, history-inferred favorites, promotional entries or network feed behavior was copied.
